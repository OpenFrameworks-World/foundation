# OpenFrameworks Primer

## A Design System for Frameworks

OpenFrameworks is a design system for representing, composing, publishing, governing, trusting, and operationalizing frameworks.

It starts from two constitutional principles:

```text
Everything is a framework.
Everything must be composable without losing capability.
```

These principles define how OpenFrameworks sees the world, how the foundation is structured, and how the platform should operate.

---

## 1. Why OpenFrameworks Exists

Organizations are full of frameworks, whether they name them or not.

They have:

- operating frameworks
- policy frameworks
- control frameworks
- governance frameworks
- architecture frameworks
- decision frameworks
- learning frameworks
- risk frameworks
- value frameworks
- implementation frameworks

Most of these frameworks live as scattered documents, spreadsheets, diagrams, slide decks, tools, rules, workflows, and tribal knowledge.

They are often hard to discover, hard to compare, hard to govern, hard to reuse, and hard to trust.

OpenFrameworks exists to turn those scattered structures into governed, publishable, composable, trusted framework assets.

---

## 2. The Two Principles

### Principle 1: Everything Is a Framework

A framework is a reusable structure that represents capability.

A framework may describe how something is:

- understood
- organized
- governed
- evaluated
- operated
- taught
- improved
- reused
- composed

Under this principle, policies, controls, architectures, methods, standards, protocols, operating models, and decision models can all be represented as frameworks or framework elements.

### Principle 2: Everything Must Be Composable Without Losing Capability

A framework must be designed so it can compose with other frameworks without losing its original capability.

Composition must preserve:

- meaning
- identity
- provenance
- governance
- trust
- lifecycle
- operational usefulness

The goal is not to merge everything into one large monolith.

The goal is to let frameworks combine into larger systems while preserving the capability of each part.

---

## 3. The Theory of Composition

The Theory of Composition explains how frameworks become systems.

```text
Framework + Framework = Framework
```

A composition is valid only when every participating framework preserves its declared capability and the composed whole creates additional useful capability in a declared context.

Composition is not aggregation.

Aggregation places things together.

Composition makes them work together.

Composition is not absorption.

Absorption destroys identity.

Composition preserves identity.

Composition is not replacement.

Replacement substitutes.

Composition cooperates.

The core theorem is:

```text
The world can be represented as a recursively composable framework graph.
```

## 4. OpenFrameworks as a Design System

OpenFrameworks is not only a registry or catalog.

It is a design system.

Just as a user-interface design system defines reusable components such as buttons, cards, typography, spacing, and layouts, OpenFrameworks defines reusable framework primitives such as:

- Framework
- Framework Card
- Framework Blueprint
- Operating Model
- Architecture Model
- System
- Value Model
- Outcome
- Measurement
- Evidence
- Trust
- Certification
- Accreditation
- Adoption
- Feedback

These primitives let organizations design and operate framework systems consistently.

## 5. The Canonical Stack

The OpenFrameworks stack is:

```text
Framework
  -> Framework Card
  -> Framework Blueprint
  -> Operating Model
  -> Architecture Model
  -> System
  -> Value Model
  -> Outcome
  -> Measurement
  -> Evidence
  -> Trust
  -> Certification
  -> Accreditation
  -> Adoption
  -> Feedback
  -> Foundation Evolution
```

Each layer answers a different question.

| Layer | Question |
|---|---|
| Framework | What capability exists? |
| Framework Card | How is the capability represented? |
| Framework Blueprint | How do frameworks compose? |
| Operating Model | How does the composition behave? |
| Architecture Model | How is the behavior designed for implementation? |
| System | How is it implemented in reality? |
| Value Model | What value should it create? |
| Outcome | What changed? |
| Measurement | How was change measured? |
| Evidence | What proves the claim? |
| Trust | How much confidence should we have? |
| Certification | What has been formally verified? |
| Accreditation | Where is it approved for use? |
| Adoption | Who uses it? |
| Feedback | What should change? |

## 6. The Framework Card

The Framework Card is the atomic publishable unit of OpenFrameworks.

Every framework must have a Framework Card before it can be validated, composed, published, trusted, certified, accredited, adopted, or measured.

A Framework Card declares:

- identity
- classification
- capability
- context
- composition metadata
- governance
- evidence
- trust
- lifecycle
- publishing status

The registry stores Framework Cards.

The graph connects Framework Cards.

The publishing system publishes Framework Cards.

The trust engine scores Framework Cards.

The certification system certifies Framework Cards.

---

## 7. The Framework Blueprint

A Framework Blueprint is a governed composition of Framework Cards.

A card describes one framework.

A blueprint describes how multiple frameworks compose into a larger framework.

Example:

```text
Identity Framework Card
+ Policy Framework Card
+ Control Framework Card
+ Trust Framework Card
= Identity Governance Blueprint
```

A blueprint must declare:

- participating framework cards
- composition contract
- preserved capabilities
- added capabilities
- interfaces
- evidence
- governance
- trust
- publishing status

---

## 8. Operating Model, Architecture Model, and System

A Framework Blueprint describes structure.

An Operating Model describes behavior.

An Architecture Model describes implementation design.

A System is the implemented reality.

```text
Blueprint = structure
Operating Model = behavior
Architecture Model = design
System = implementation
```

This distinction prevents OpenFrameworks from confusing ideas, designs, workflows, architectures, and real systems.

---

## 9. Publishing Is the Gate

Publishing is the activation gate.

A framework is not authoritative because it exists in a repository.

A framework becomes authoritative only when it is published through a governed publishing process.

```text
Draft is not authority.
Merge is not authority.
Publishing is authority.
```

A published artifact must have:

- stable identifier
- version
- owner
- reviewer
- approver
- provenance
- license declaration
- governance status
- conformance status
- release notes
- lifecycle state

Publishing turns framework knowledge into a governed asset.

---

## 10. Trust, Evidence, Certification, and Accreditation

OpenFrameworks treats trust as earned, not assumed.

A claim must be supported by evidence.

A composition must be validated.

A trust score must be explainable.

Certification verifies that a framework meets defined foundation criteria.

Accreditation verifies that a framework or composition is approved for use in a specific organizational context.

Certification is asset-centric.

Accreditation is context-centric.

Trust does not automatically transfer through composition.

A composed framework needs its own trust record.

---

## 11. Vendor Neutrality

OpenFrameworks separates:

```text
Capability
Framework
Standard
Protocol
Implementation
Product
Vendor Service
```

This prevents framework governance from becoming vendor marketing.

A framework recommendation must declare:

- alternatives
- tradeoffs
- lock-in risks
- evidence
- assumptions
- context
- confidence

No recommendation should be based only on popularity, sponsorship, market share, or vendor preference.

---

## 12. The Living Graph

The OpenFrameworks graph is not static.

It must close the loop from design to implementation to value to feedback.

```text
Published Framework
  -> Adoption
  -> Measurement
  -> Evidence
  -> Trust
  -> Feedback
  -> Foundation Change Proposal
  -> New Release
```

This loop prevents the foundation from becoming a static standards repository.

The platform exercises the foundation.

Real adoption creates evidence.

Evidence changes trust.

Feedback improves the foundation.

---

## 13. Foundation and Platform

OpenFrameworks Foundation defines the contract.

OpenFrameworks Platform operationalizes the contract.

```text
Foundation = design system contract
Platform = authoring, validation, publishing, registry, graph, workflows, search, trust, certification, accreditation, and measurement
```

Foundation should define meaning, schemas, rules, publishing gates, and conformance.

Platform should implement authoring, validation, registry, graph, publishing, and operating workflows.

---

## 14. Learning and Enterprise Adoption

OpenFrameworks is also a learning system.

It teaches organizations how to build their own framework design systems.

The commercial offering is not only software.

It includes:

- education
- templates
- workshops
- certification
- platform implementation
- enterprise framework design systems
- governed framework offices

The product is the design system.

The platform operationalizes it.

The foundation keeps it open, governed, and trustworthy.

---

## 15. The Core Statement

```text
Everything is a framework.
Everything must be composable without losing capability.
Composition turns frameworks into systems.
Systems create value.
Publishing activates authority.
Evidence earns trust.
Feedback keeps the foundation alive.
```

This is the OpenFrameworks worldview.
